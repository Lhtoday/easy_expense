# ExpenseFlow Frontend Rules

本文件用于约束前端开发。当前端目录内还有更深层级的 `AGENTS.md` 时，以更靠近代码的规则为准。

## Stack

- React + TypeScript + Vite
- Ant Design
- TanStack Query
- Zustand
- React Hook Form + Zod

## UI Principles

- 界面应偏向财务和运营工具风格：清晰、克制、可扫描、高信息密度。
- 不做营销式首页，第一屏应直接进入可操作工作台或列表。
- 常见工作流必须高效：新建报销单、草稿保存、提交审批、审批处理、财务审核、付款登记、凭证查看。
- 所有按钮、表格、表单、筛选器、状态标签和弹窗应保持一致的视觉体系。
- 不在页面里写大段功能说明，业务含义应通过清晰字段、状态、提示和操作反馈体现。

## Page Rules

- 报销单编辑页应支持草稿保存、明细行编辑、附件上传、发票关联和费用政策提示。
- 审批页应突出金额、超标信息、预算影响、发票异常和历史审批意见。
- 财务审核页应突出科目、税额、成本中心、预算、发票校验结果和凭证预览。
- 列表页必须支持分页、排序、筛选、状态标签和批量操作入口。
- 表单提交失败时，应把错误定位到具体字段或具体明细行。

## State And Data

- 远程数据请求优先使用 TanStack Query。
- 只把跨页面、跨组件且确实需要共享的 UI 状态放入 Zustand。
- 表单状态优先由 React Hook Form 管理。
- 表单校验 schema 优先使用 Zod，并与后端 DTO 语义保持一致。
- 前端可以做费用政策提示和基础校验，但最终以后端校验结果为准。

## TypeScript Rules

- 禁止用 `any` 绕过核心业务类型，尤其是金额、状态、权限、审批动作、费用类型和发票字段。
- 枚举值应集中定义或从 API 类型生成，避免散落硬编码字符串。
- 金额字段在展示层必须明确单位和格式，不直接拼接未格式化数字。
- 后端返回结构变化时，应优先更新类型定义，再调整组件。

## Component Rules

- 复杂业务页面应拆分为页面容器、查询区域、表格区域、表单区域和操作组件。
- 通用组件只沉淀真实复用的交互，不为了抽象而抽象。
- 表格列、状态标签、金额展示、附件预览、审批记录等高频 UI 可以提炼为业务组件。
- 不在组件内直接写复杂财务判断，复杂规则由 API 返回结果驱动展示。

## Testing Rules

- 关键页面至少覆盖渲染、提交、校验失败、权限隐藏和异常提示。
- 金额格式化、状态标签、审批操作、表单校验应有单元测试。
- 对接 API 的页面应 mock 成功、失败、空数据和权限不足场景。
